# CLAUDE.md

Guidance for Claude Code when working in this repo.

## What this is

**P.A.K.S.** is a 2D browser platformer (stickman parkour in an office-elevator theme) built by four students for UWT's TCSS 491 (Game and Simulation Design). Think Mr. Fancy Pants + Super Meat Boy + N++: momentum-based movement, speedrun timer, no enemies to kill, only hazards to dodge. The course is over. We are now modernizing it as a hobby/portfolio project.

Everything lives in `GameEngine/`. It is vanilla JS on an HTML5 canvas (a fixed 1900x1025 view, drawn at the screen's resolution), with everything drawn as vector shapes: there are no sprite images left. **There is no build step, bundler or package.json.** Pure-logic and headless-physics tests run with Node's built-in runner: `node --test` from the repo root (Node 20+, no dependencies).

## Run it

```bash
cd GameEngine && python3 -m http.server 8000   # open http://localhost:8000
node --test                                    # from the repo root: run the automated tests
```

Use a local server, not `file://`. Tick the **Debug** checkbox in the page to see hitboxes, a level selector, "Unlock All Levels" and click-to-teleport. In debug mode, dying and winning are disabled. The **LEVEL EDITOR** button on the title screen opens the level editor (see "Level editor" below).

## Architecture (as it exists today)

- **Script tags, global scope.** `index.html` loads every `.js` file with plain `<script>` tags. **Load order matters** (e.g. `gameengine.js` and `levelconfig.js` before entity files, `main.js` last). New files must be added to `index.html` in the right place. Classes and managers are globals.
- **Engine:** `gameengine.js` owns the loop, input (`game.keys`, lowercase keys like `'a'`, `' '`, `'shift'`), `game.entities`, `game.clockTick`, `game.options.debugging`, and references such as `game.Player`, `game.timer`, `game.levelUI`, `game.levelConfig`, `game.levelTimesManager`.
- **Entities** implement `update()` and `draw(ctx)`, have a `BB` (`BoundingBox(x, y, w, h)` with `left/right/top/bottom` and `collide()`), and are removed by setting `removeFromWorld = true`. Add them with `game.addEntity()`.
- **Levels:** Each floor is a JSON file in `GameEngine/levels/level_00.json` … `level_16.json`. `main.js` fetches all 17 at startup (requires HTTP server — `fetch()` fails on `file://`) and stores them in `window.LEVEL_LOADER` (a `LevelLoader` instance from `levelLoader.js`). `LevelConfig.loadLevel(n)` calls `LEVEL_LOADER.getLevelEntities(n, game, TILE_SIZE)` which returns `{ map, player, exitDoor, hazards, tiles }` factories and hands them to `LevelConfig.assemble(cfg)`, which clears the world, builds the map (`tiles`, a 2D array, goes to `drawMap.loadMap()`), exit, hazards and player, and resets the timer. `assemble` is separate from `loadLevel` so a level that is not a numbered floor (the editor's playtest) can be built without touching `currentLevel`, progress or best times. The level files are kept in the editor's canonical layout (one tile row and one entity per line): after editing one by hand run `node scripts/format-levels.js` (a test checks this). `drawMap.js` handles tile collision and draws the visible tiles. Tile ids in `map.tiles`: `0` empty, `1` full block, `10`-`73` sloped/curved shapes (see "Sloped and curved tiles" below); unknown ids load as empty with a console warning. `checkCollisions(entity)` reports any tile hit (full blocks, then shapes via SAT against `entity.BB`); `checkSolidTiles(entity)` is the original full-blocks-only test. Floor 0 is a test level, 76 tiles wide: a slope/curve playground along the bottom-left, and a bay to the right of it (columns 46-75) for the gentle and steep shapes. Floor 0 is meant to be edited, so tests that need its layout read `tests/fixtures/slope-playground.json` instead, floors 1-12 are the main run, and 13-16 are mystery floors unlocked after 12.
- **Player** (`player.js`): state machine (idle, walking, running, skidding, crouching, sliding, jumping, falling, wall sliding). Physics constants (`MIN_WALK`, `MAX_RUN`, `ACC_*`, `DEC_*`, `MAX_JUMP`, etc.) are declared at the top of `update()`. Collision is AABB: minimum-overlap resolution against `BigBlock`s, snapping to tile edges for full blocks, and the slope handling described below for shaped tiles. Death is triggered in `update()` by overlapping `Projectile`, `Spike` or `GlowingLaser`. Platforms (`platform.js`) are one-way, can move and carry the player.
- **Sloped and curved tiles** (`tileShapes.js`, plus `drawMap.js` and the tile-collision half of `player.js`):
  - `tileShapes.js` is pure geometry with no DOM or game dependencies (a global in the browser, `require()`-able in Node). It defines 28 shapes as convex pieces plus an outline for drawing, and SAT between an AABB and a piece. A contact carries the push-out normal and depth, is classified `floor` (surface within ~45° of flat), `ceiling` or `wall`, and carries the straight-up (`up`) and straight-down (`down`) clearance. Push-out directions come only from *exposed* piece edges, never the box's own axes or the hidden inner rays of the concave shapes' triangle fans; otherwise a box clipping a seam reports phantom walls.
  - Ids (letters name the corner holding the solid mass: BL, BR, TL, TR): `10-13` `SLOPE_*` 45° triangles, `20-23` `CONVEX_*` quarter discs (rounded shoulders), `30-33` `CONCAVE_*` quarter-pipes. Arcs are 8-segment polygons (about 0.1px off a true circle at 25px tiles).
  - Ramps built from two tiles: `40-43` `GENTLE_HIGH_*` and `50-53` `GENTLE_LOW_*` make a 26.6° ramp 2 tiles wide and 1 tall (LOW at the low end, HIGH at the tall end); `60-63` `STEEP_TIP_*` and `70-73` `STEEP_BASE_*` make a 63.4° face 1 tile wide and 2 tall (TIP on top of BASE). Gentle ramps are walkable like the 45° ones, steep faces are `wall` contacts that block and are never clung to. No physics change was needed: `SLOPE_MAX_RISE = 1` is an upper bound and the 26.6° rise per pixel is 0.5.
  - Player movement on shapes: horizontal speed and all physics constants are unchanged (no slope momentum). Walkable surfaces (up to 45°) never block; the player is lifted straight up onto them, so feet follow the surface exactly. `moveAlongShapes` moves in ~1px steps, lifting after each, because probing a whole frame's move from the old height sees the next tile's tip poking in from below, which looks like a wall at every seam of a diagonal ramp. `resolveShapeContacts` pushes out after the vertical move (floors up, ceilings down, steeper-than-45° faces along the surface normal, in up to four passes) and snaps the player back down going downhill (at most `|dx|·1 + 2` px). `tryStepUp` steps onto a full block whose top is within one slope-rise, e.g. a ramp that ends level with a ledge. Steeper-than-45° faces block movement but are never clung to (wall-stick only ever happens against full blocks). `footDrop()` draws the sprite lower so the feet look planted; it is visual only.
- **Camera and view** (`camera.js`, plus `gameengine.js`, `drawMap.js`, `autoScreenResizer.js`): the canvas is a **fixed 1900x1025 view (76x41 tiles)**, not as big as the level. Every original floor (76 wide, 36-41 tall) fits, so it is shown whole and centred with black around it; a bigger level scrolls, the camera easing toward the player and never letting them leave the middle of the view. Tiles and sprites therefore stay the same size on screen at any level size, and the HUD stays the same size. `camera.js` is pure logic (global `Camera`, `require()`-able): follow/snap, clamp, and pan/zoom/fit for the editor. The engine draws the world through `camera.transform()` and the timer, `LevelUI` screens and debug text outside it; `drawMap` paints its own area only and only the tiles in view (levels up to 300x300 are fine). `autoScreenResizer.js` fits the view to the window with one rule (`min(window / canvas)`, exposed as `window.fitGameCanvas`), so 1080p, 1440p and a laptop all show the same field of view; the old 1/0.75/0.5 steps chosen from the screen size are gone. Pointer positions must go through `game.pointerToCanvas(e)` (screen UI) or `game.pointerToWorld(e)` (level position): raw `clientX - rect.left` is wrong under CSS scale (this fixed the death/complete screen buttons and debug click-to-teleport). **Full resolution:** the view is `game.viewW x game.viewH` *view pixels* (the camera's view size) and everything is drawn and hit-tested in those; the canvas's pixel buffer is `pixelRatio` times bigger, where `targetPixelRatio()` = CSS fit scale (measured from `getBoundingClientRect`) x `devicePixelRatio`, capped at `GameEngine.MAX_PIXEL_RATIO` (2). `draw()` calls `syncPixelRatio()` each frame (it only resizes the buffer when the ratio really changes: window resize, browser zoom, another screen), sets the base transform `scale(pixelRatio)` and draws the world through `camera.transform(pixelRatio)`, which rounds its translation in device pixels. So **never read `canvas.width/height` as the view size**: use `game.viewW/viewH`. Assigning `canvas.width` resets the context, so `applyPixelRatio()` turns image smoothing back on. `game.cameraManual` lets the editor drive the camera.
- **Level editor** (`levelModel.js`, `levelEditor.js`, `levelEditorUI.js`; opened by the title screen's LEVEL EDITOR button, which calls `startGame({editor: true})` in `main.js`):
  - `levelModel.js` is pure logic like `tileShapes.js` (global `LevelModel` in the browser, `require()`-able in Node). It holds the per-entity-type field schema (drives both the inspector forms and validation), entity boxes and hit-testing (`boundsFor`, `pick`), tile edits (`setTile`, `fillRect`, `floodFill`, `resize`), the snapshot undo `History`, `validate()` (errors block playtest and import; warnings are advisory, e.g. a spawn that overlaps a block, a slope shape or a solid big block: the engine pushes the player out of it, so stand the spawn on top of it instead) and `serialize()`, the canonical file format. The level object is exactly the JSON the game loads: **the editor adds no fields and unknown fields round-trip untouched**, so `levelLoader.js` needed no change.
  - `levelEditor.js`: while editing, the engine's entities are just a `drawMap` (so tiles and background look as in the game) and an overlay that draws each entity with its real class but never `update()`s it, so nothing moves or fires. Tools: brush, rectangle (Shift = outline), fill, pick, select; right-click erases; entity placement; a per-type inspector; spawn and exit are always present and movable; snap of 1/5/25px; undo/redo; resize with a warning before cutting content. **Playtest** (P) builds the draft with `LevelConfig.assemble` and swaps `game.levelUI` for `PlaytestUI` (in the same file), so dying shows a retry screen and winning a clear time, and no best time, unlocked floor or `CURRENT_GAME_LEVEL` is ever written. Debug mode still disables dying and winning, which makes a god-mode playtest.
  - Files: the editor works on `LEVEL_LOADER.levels` clones (**Open floor**) or files (**Open file…**). **Save overwrites the level's own file**: the file it was opened from or last saved to, or, for an opened floor, `level_NN.json` in the levels folder. A browser cannot know where the repo is, so the first such Save asks for the `GameEngine/levels` folder (the picker also accepts its parent; it must contain `level_00.json`) and the editor remembers it as a directory handle in its own IndexedDB `paks-editor` (separate from the game's saved progress; the browser re-asks permission after a restart; **Levels folder…** changes it). Saving a floor also updates `LEVEL_LOADER.levels[n]`, so the game and the floor picker see it without a reload. **Save as…** always asks for a file. Without the File System Access API (Firefox, Safari) both download and Open file uses a file input. An autosaved draft lives in `localStorage` key `paks.editor.draft` (offered for restore on the next open). Custom levels are not yet playable from the Levels screen.
  - While editing, the canvas is exactly the space between the panels, drawn 1:1, and the editor pans and zooms the shared camera over the level (wheel zooms at the cursor, Space+drag or middle-drag pans, `0` fits the level, `1` is 100%, arrows pan when nothing is selected); a playtest switches to the game's own view and follows the player, so it looks and scrolls exactly like the game, then restores the editing camera. `EditorUI.LEFT/RIGHT/TOP/BOTTOM` are the panel sizes. `gameEngine.hideHud` hides the floor-time panel while editing, and `LevelUI.handleKeyDown` stands down during a playtest so M/L cannot leave the editor.
- **Tutorial** (`tutorial.js`, `hint.js`, `levels/tutorial.json`, plus small branches in `levelconfig.js`, `LevelUI.js`, `welcomeScreen.js`, `main.js`): a short untimed level that teaches walking, sprinting, jumping (and holding for height), spikes, sliding under a laser, wall jumping, levers and the exit door.
  - **It is not a numbered floor.** `main.js` fetches `levels/tutorial.json` into `LEVEL_LOADER` under the key `Tutorial.LEVEL_KEY` (`'tutorial'`), so floor numbers, best times, saved progress, the Levels screen and the hard-coded level counts never see it. It is a 76x41-tile room in two tiers (bottom tier left to right: step, spikes, tall box, low ceiling with a laser under it, then a wall-jump shaft up to the top tier: lever on a box, exit). Edit it in the level editor with **Open file…** (it is not in the **Open floor** list); `scripts/format-levels.js` and `level-format.test.js` cover it like the floors.
  - `tutorial.js` is pure logic like `camera.js` (global `Tutorial`, `require()`-able): the one `localStorage` flag `paks.tutorialDone` (deliberately not the IndexedDB save, so the save format is unchanged), `storage()` (guarded, because even reading `localStorage` can throw), and `shouldAutoStart(storage, progress)`: only on a first Start, i.e. flag unset **and** no completed floor (someone who played before the tutorial existed is not sent to it), and never when the browser can't remember the answer.
  - `Hint` (`hint.js`, level entity `{type:"Hint", x, y, w, h, text}`, in `LevelLoader` and the `LevelModel` schema, so the editor places and edits it): a sign drawn in the level, never solid. `[Key]` in the text is drawn as a key cap. `Hint.layout()` wraps text with a `measure` function and is pure; the font is monospace on purpose so a sign lays out the same everywhere and tests can check the text fits. Signs are dimmed (`Hint.DIM`) until the player is near.
  - `LevelConfig.loadTutorial()` builds it with `assemble()`, sets `levelConfig.tutorial = true` and `game.hideHud = true` (no timer panel); `loadLevel()` clears both. `LevelUI` branches on `isTutorial()`: clearing it records no best time and marks the tutorial done, the clear screen says TUTORIAL COMPLETE and Enter goes to floor 1 (`leaveTutorial()`), Retry reloads the tutorial, and a canvas-drawn **SKIP TUTORIAL** button (`LevelUI.SKIP_BUTTON`) marks it done and starts floor 1. `Esc` could not be the skip key because the in-game menu owns it.
  - Entry points: the first Start on a fresh profile (`WelcomeScreen.shouldStartTutorial()`), the **TUTORIAL** button on the title screen (`startGame({tutorial: true})`), and "Tutorial" in the debug floor picker. **Reset Progress now clears everything**: unlocked/completed floors, all best times and the tutorial flag (it used to leave best times alone). Volume and the editor's draft are settings, not progress, and stay.
  - Design numbers, measured with the real `Player` at 60 fps (useful for any future level): a full jump rises 173px (7 tiles) and covers about 190-330px sideways (a tap rises about 62px); walking tops out at 400px/s. **Crouching and sliding only shrink the hazard box** (`Player.BB`: the lower half or lower third); tile collision is always the full 20x74 box, so a slide is for dodging lasers and projectiles, never for fitting under a low ceiling. Releasing Shift caps speed at 400px/s, so a slide carries at most about 263px however fast you were running; a slide that stops inside a beam leaves you crouched in it, and standing up kills you, so keep beams short (the tutorial's is 50px, with a timing window of about 180px). Wall-jump shafts from 4 to 12 tiles wide all climb; the tutorial's is 9. Tile edges must sit on the 25px grid: an entity can be anywhere, but `LevelModel.fillRect` with fractional tile indices silently writes garbage (a box built from off-grid pixels was never solid until a headless run showed the player walking through it).

The level 0 tests in `player-slopes.test.js` read `tests/fixtures/slope-playground.json`, a frozen copy of the test floor, so editing the real level 0 (which the editor is for) cannot break them; do the same for any test that hard-codes a level's layout. `helpers/browserScripts.js` loads the browser `<script>` files into a Node `vm` context with stubbed globals, so no browser or build step is needed. `helpers/headless.js` plays a whole level JSON with the real `LevelLoader`, `LevelConfig.assemble` and `Player` at 60 fps with scripted keys; its timers run on the game's clock, so the wall-jump cooldown and the death-screen delay behave as in the browser, and it throws if a level touches the best-time store.
- **Vector stickman** (`stickman.js`, drawn by `player.js`; roadmap item 6, part 1):
  - `stickman.js` is pure logic like `camera.js` (global `Stickman`, `require()`-able): a skeleton (head, torso, two-bone arms and legs sized to the 20x74 hitbox) posed by joint angles, forward kinematics (`solve`), two-bone IK for legs and arms (`legIK`, `armIK`), one clip per state and drawing. Local coordinates put the origin at the middle of the box's bottom edge, x the way the figure faces.
  - Clips: `idle` (breathing), `gait` (walk and run are one gait, so Shift never snaps the legs), `skid`, `crouch` (a deep squat with the chest up and the arms folded at chest height, like the Cossack squat dance; `SQUAT` holds its shape), `slide`, `jump` and `fall` (keyed on `vy`), `wall` (back to the wall, a hand and a foot on it). Grounded clips place the feet by IK, so a foot on the ground is exactly on it. The gait's phase advances by **distance travelled** (`|vx|·dt / stride`), so a planted foot never slides; the step rate is chosen first and rises steadily with speed, and the stride follows from it (blending walk and run shapes by speed made the legs slow down as the body sped up). A run has a flight phase; a slow walk never does.
  - `Stickman.Rig.update(dt, {state, vx, vy, grounded, facing, wallSide})` crossfades between clips. The crossfade is longer for a bigger change of pose (0.1-0.24 s, from the joint travel measured along the blend), the direction each angle blends is fixed when the blend starts (picking the shortest way every frame flipped a running arm mid-blend), `vy` and speed are smoothed within a clip (releasing jump halves `vy` in one frame), turning round squeezes the figure through zero width over 0.12 s, and a hard landing squashes it briefly. Long frames are capped at 0.1 s.
  - `Player` holds `this.rig` and advances it **in `draw()`**, never in `update()`: it only reads the physics, so movement is untouched and the headless tests, which never draw, see no difference. `Player.RIG_STATES` maps `this.STATES` numbers to clip names, `rigInput()` builds the input, and `drawShadow()` puts a soft ellipse on the ground (`map.getDropDistance`, tiles only, fading out by about 180px up; none over platforms while airborne). The feet go at the box bottom plus `footDrop()` as before.
  - `Stickman.STYLE` (colours, line width, head radius) is separate from the rig so a skin later is just another style object. Far limbs are drawn first and lighter, the head has a soft highlight.
  - Death: `DeathAnimation(x, y, segments)` takes `Stickman.segments(joints)` from the pose the player died in and throws each piece (`DeathLimb` in `deathParticle.js`: rigid, spinning, gravity, fading by about 0.9 s). **The game clock is 0 while the player is dead** (`kill()` stops the floor timer, which is also the frame clock), so `Player.draw` times the pieces with `Date.now()` and passes that as `update(clockTick, pieceDelta)`; the red splatter keeps its old per-frame fade and doesn't move, as before. Without segments the old generic body parts are used.
- **Vector entities** (`entityArt.js`, global `EntityArt`, pure drawing): `spike` (two-tone saw with a real hole and faint spin ghosts), `projectile` (small saw with a trail; no longer fired by anything, kept for a future hazard), `rocket` (a classic bottle rocket: red paper tube, a wider cone cap whose lip overhangs it and a long wooden stick; a black fuse while loaded, a flickering flame and sparks in flight), `firework` (the burst: a flash, then coloured streaks that slow, droop, crackle and fade over `FIREWORK_LIFE` = 1.1 s; repeatable from a seed), `launcher` (rotated by `shotdirec`; its existing `time` since the last shot drives a recoil, a muzzle flash, the barrel standing empty for 0.15 s and the next rocket sliding in, its fuse sparking and a charge light warming up before each shot), `lever`, `exitDoor` and `platform` (a steel bar with a dark rounded outline, the old sprite's size). Each keeps its old sprite's footprint (the lever is drawn 36.5x53.5 over its 23x53 box, the door `width·scale x height·scale`), and `BB`s are unchanged. Animation progress lives on the entity and is advanced in `draw()`: `Lever.flip` (the handle swings down over 0.2 s, the knob turns red → green) and `exitDoor.openAmount` (doors slide open over 0.6 s once unlocked, onto a lit car). `GlowingLaser` and `Hint` draw themselves; so does the old `Laser` class (a red line; level 0 uses it).
- **Rockets** (`enemies.js`): `ProjectileLauncher` fires `Rocket`, a `Projectile` subclass, so the 30x30 box, speed, wall handling and the player's `instanceof Projectile` hazard check are all unchanged (only the look is new). A rocket `explode()`s once, into a `FireworkBurst` entity at its centre, when `Projectile.update` removes it on a wall or big block, or when the player is hit (`Player` calls `entity.explode` if it has one). `FireworkBurst` is drawing only and ages on the real clock in `draw()` (the game clock is 0 once the player dies); it removes itself after `FIREWORK_LIFE`.
- **Vector tiles** (`tileArt.js`, global `TileArt`, pure drawing; `drawMap` calls `TileArt.drawTiles` for the rows and columns in view): each level's theme colour is `TileArt.PALETTE[map.random2]`, the eight flat colours the old block images were, so the random and coordinated themes are unchanged. Each row's runs of full blocks are filled as one rectangle that overlaps solid neighbours by `OVERLAP` (0.75px), and edge bands are merged into runs too: at a fractional screen scale, shapes that merely touch leave a faint seam. Exposed sides get a band: tops lighter, bottoms darker, sides a little of each (`EDGE`); a side counts as covered when the neighbour is a block, or a shape whose solid part touches that side (`exposedSides`, compared with a 0.01px tolerance because arc ends come from sin/cos). Sloped and curved tiles are filled, stroked in the same colour to close seams, and their slanted or curved surface lit by which way it faces. Big blocks get the same top and bottom bands (`drawBigBlock`; their colours are hex now, exactly the old named colours, so they can be shaded).
- **Vector menus** (`uiArt.js`, global `UIArt`, pure SVG markup builders, `require()`-able): the title screen (`titleBackground`: wall, rings, gears, block cluster and the P.A.K.S logo as text; `starButton`: four-pointed stars whose label stays within 15° of level), the Levels screen (`levelsScene` in the old 1800x1080 background's own coordinates, so every floor button and hidden mystery-floor button still sits where it did; `floorButton`, `padlock`, `toxicSign`/`radiationSign`/`cautionSign` for floors 13-15, `paksSign` for 16, `panelButton` with labels narrowed to fit, `clickLevelsHeader`), the instructions sheet (`instructionsSheet` is HTML with real text; `paintInstructionArt` draws its hazards, levers and door with `EntityArt` into canvases marked `data-art`) and the in-game menu icon (`menuIcon`, used as a background through `dataUri`). Menu buttons are `<div>`s holding inline SVG, not `<img>`s, so text can use the Molot web font (an SVG loaded as an image can't). `mountStickman(canvas, {pose})` runs the game's own rig in a menu: leaping on the title logo, idling in the Levels-screen lift; it stops by itself when the canvas leaves the page.

- **Persistence:** IndexedDB for level progress (`levelProgressManager.js` → `window.LEVEL_PROGRESS`) and best times (`leveltimesmanager.js`); `localStorage` for volume, the level editor's unsaved draft and whether the tutorial is done (`paks.tutorialDone`). Reset Progress (Levels screen) clears all of the game's progress: unlocked/completed floors, every best time and the tutorial flag.
- **UI:** built with DOM elements and inline styles (welcome/elevator screen, levels screen, in-game menu, volume panel) plus canvas-drawn level-complete and death screens in `LevelUI.js`.
- **Globals to know:** `ASSET_MANAGER`, `AUDIO_MANAGER`, `GAME_MENU`, `LEVEL_PROGRESS`, `VOLUME_CONTROL`, `CURRENT_GAME_LEVEL`, `window.gameEngine`.

## Known tech debt and gotchas

- The level count is hard-coded in several places (`LevelsScreen.js` uses 12 and 13-16 ranges, `levelProgressManager.js` uses 12). Adding a level means touching those files.
- `levelProgressManager.js` monkey-patches both `LevelConfig.prototype.loadNextLevel` **and** `LevelConfig.prototype.loadLevel` at runtime. Fragile. The fallback code inside the patched `loadNextLevel` (used if the original method is somehow absent) hard-codes `< 12`, so the game would cap at level 12 in that edge case.
- `Player.update()` is very large. Wall-jump cooldowns use `setTimeout` instead of the game clock.
- Sound effects create a new `Audio` object per play. The elevator "ding" is commented out.
- Level JSON files are fetched at startup. The game **requires an HTTP server** (`python3 -m http.server`, VS Code Live Server, etc.) — opening `index.html` directly via `file://` will fail to fetch JSON and all levels will refuse to load.
- File `volumnecontrolui.js` has a typo in its name. Rename only if you update `index.html`.
- Music tracks in `sounds/` need license/attribution review.
- `loadNextLevel()` checks `this.currentLevel < 17`, which still allows it to attempt a non-existent level 17 after the final floor. However `LevelUI.js` now intercepts "continue" on level 16 and shows a "Game Complete" / Home screen instead.
- A `BigBlock` whose corners are reversed (`y2 < y` or `x2 < x`) gets a negative-size box in the game: it draws but never collides. Level 14 had two and they were fixed by hand; the editor warns about any new one and `levelModel.test.js` requires every real level to be warning-free.
- `window.LEVEL_PROGRESS` only exists once something creates it (`LevelsScreen`, or the first-Start tutorial check), so code that needs it elsewhere must create it the same way (`new LevelProgressManager()`).
- `GameMenu` is created once, for the first engine, and `Esc` toggles it, so `Esc` is taken in a game. `window.LAST_ENGINE` is the engine on screen: listeners that live on the shared canvas (the tutorial's skip button) check it, because every Start leaves the old engine's listeners behind.
- `window.gameEngine` is never assigned (despite being listed as a global), so `WelcomeScreen.goToGame`'s "resume" branch never runs and every Start builds a fresh `GameEngine` on the same canvas. Old loops are not always stopped (`LevelUI`'s Home/Levels buttons only pause), so `main.js` records `window.LAST_ENGINE` and the editor stops it before taking over. `isPaused` is set by the menu but never read by the loop.
- Level 14 has two duplicate `Lever` objects placed at identical coordinates `(24, 170)` and `(1853, 170)`.
- **Full-block corner clip (pre-existing, left alone to preserve feel):** `Player.handleCollisions` builds the vertical-pass box with the pre-move `x`, so a diagonal move can nick a full block's corner by up to ~3px at 60fps (~6px with slow frames). It resolves itself. The untouched game does it too; `player-slopes.test.js` tolerates up to 4px of it (`CORNER_CLIP`) but never any overlap with a shape.
- **Slope limits:** the hitbox rests on its higher corner on a slope (the stickman is drawn lower to compensate; its legs don't bend to the slope angle). Only 45° and 26.6°/63.4° slopes and quarter circles exist, and no arbitrary polygons (add pieces to `tileShapes.js` when needed). A ceiling contact blocks a grounded player moving under it rather than sliding along it. Frame-time spikes can tunnel through geometry, same as full blocks; fixed-timestep physics is on the roadmap.
- **The death and complete screens' buttons only answer once the mouse has moved over the canvas** (`LevelUI` attaches its click handler in the hover code). A real player always has; a scripted browser test must send a mouse move before clicking.
- **`clockTick` is 0 while the player is dead:** `Player.kill()` stops `game.timer`, which is both the floor time and the frame clock. Anything that should animate behind the death screen needs its own clock (the death pieces use `Date.now()`). `Timer.tick()` also logs "Tick called while not running" every frame while stopped.
- `LevelProgressManager.unlockAllLevels()` (the instance method) only loops levels 1–12 due to `NUMBER_OF_LEVELS = 12`. The global `window.unlockAllLevels()` function handles levels 13–16 separately. The two functions are not equivalent.

## Working agreements

- **Keep the game playable at every commit.** Prefer small, reviewable changes over big-bang rewrites. Work on a branch.
- **Preserve game feel.** Do not change physics constants or movement behavior unless the task is about movement, and call out any such change explicitly.
- Run `node --test` after changes (all tests must pass), then run the game and check `docs/SMOKE_TEST.md`; the automated tests cover collision and movement logic, not UI, audio or persistence. Quick pass: welcome screen → start → move, jump, wall jump, slide → die → restart → complete a level → best time saved → levels screen shows progress. If you add pure-logic code (collision, level parsing), add tests for it. When a browser run shows a bug the tests missed, add the test that would have caught it.
- If you introduce a build tool, ES modules or TypeScript, do it as its own dedicated change and update this file and the README.
- Match the existing style unless a refactor is the point of the task. Leave comments explaining *why*.
- Ask before deleting assets, renaming public files, or changing the save format (players' saved progress lives in IndexedDB).
- Keep this file and `README.md` current when architecture or run instructions change.
